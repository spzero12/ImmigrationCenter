# Спецификация: Генерация документов и сканы (Этап 3)

Соответствует Этапу 3 [roadmap](../../product/roadmap.md).

## Цель

По данным сотрудника и его разрешительного документа автоматически
заполнять готовый .docx-шаблон (миграционная карта и т.п.) и отдавать
результат в .docx, а также хранить сканы уже оформленных документов
сотрудника (паспорт, виза и т.д.).

Экспорт в PDF пока не нужен — .docx достаточно (можно вернуться к этому
позже, см. «Вне рамок»).

## Решения (по ответам на вопросы)

- **Шаблонов пока нет.** Ниже зафиксирована конвенция имён плейсхолдеров —
  реальный .docx-файл от заказчика должен использовать именно её (или код
  маппинга придётся поправить под реальный файл, когда он появится).
- **Хостинг только по FTP, без SSH/Composer.** Значит `composer install`
  выполнить прямо на сервере нельзя. `vendor/` нужно собрать там, где есть
  PHP + Composer (не в этой среде — здесь PHP тоже не установлен, см.
  [tasks.md](tasks.md)), закоммитить в `composer.json`/`composer.lock` как
  описание зависимостей, а сам `vendor/` — не в git, но обязательно
  копировать в `deploy/` при выкладке (аналогично тому, как туда уже
  копируется `config/config.php` с реальными данными).
- **Сканы**: JPG, PNG, PDF, до 10 МБ на файл.
- **На этом шаге** — только спецификация, без кода.

## Единый источник общих данных сотрудника

Одинаковые поля — ФИО (по частям), номер и серия паспорта, гражданство,
дата рождения и т.п. — заполняются один раз в карточке сотрудника при
регистрации ([employee_form.php](../../../employee_form.php)) и **этими
значениями предзаполняются** во всех местах, где они нужны повторно (в
первую очередь — в форме конкретного документа перед генерацией). В
отличие от предыдущей редакции этого раздела: значения **можно
редактировать** на уровне конкретного документа (например, если в
конкретной визе фамилия написана в другой транслитерации, чем в паспорте)
— единый источник задаёт **значение по умолчанию**, а не жёстко
зафиксированное значение.

### Раздельное ФИО (решено)

`employees` получает поля `last_name` (Фамилия, обязательно), `first_name`
(Имя, обязательно), `middle_name` (Отчество, необязательно — не у всех
сотрудников есть). Это нужно, потому что российские миграционные формы
обычно требуют Фамилию/Имя/Отчество отдельными полями, а не одной строкой.

Чтобы не переписывать весь существующий код (список сотрудников, поиск,
`api/documents.php`, где сейчас используется `employees.full_name`),
`full_name` в таблице **остаётся** и продолжает автоматически собираться
из трёх частей при сохранении карточки сотрудника
(`employee_form.php`) — как раньше, но теперь это производное значение,
а не то, что вводится напрямую. Существующий код, читающий `full_name`,
менять не нужно; новый код генерации документов дополнительно получает
доступ к частям по отдельности.

### Как работает предзаполнение + редактирование

Хранить это как персистентную возможность (а не одноразовое поле формы
при скачивании), потому что архитектура проекта — CRUD поверх БД, а не
разовые сессии генерации:

- В `employee_documents` добавляется `field_overrides` (`JSON NULL`) —
  ключ/значение только для полей, которые **реально были изменены** в этом
  документе относительно единого источника (например,
  `{"last_name": "Smith"}`, если в этом конкретном документе фамилия
  написана иначе, чем в карточке сотрудника).
- `document_form.php` при отображении показывает поля Фамилия/Имя/Отчество
  и паспортные данные, **предзаполненные** текущими значениями из
  карточки сотрудника / канонического паспорта (см. ниже). Пользователь
  может их отредактировать для конкретного документа.
- При сохранении сравниваются отредактированные значения с значениями
  единого источника **на момент сохранения**: если совпадают — ничего не
  пишется в `field_overrides` (поле продолжает динамически браться из
  источника, и последующее изменение карточки сотрудника автоматически
  подхватится); если отличаются — разница сохраняется в
  `field_overrides` и уже не меняется при последующих правках карточки
  сотрудника (сознательное расхождение, а не забытое устаревшее значение).
- `document_generate.php` при подстановке плейсхолдеров сначала берёт
  значения из единого источника (`employees` / канонический паспорт), затем
  накладывает поверх `field_overrides` этого документа, если они есть.

### Паспортные данные — особый случай

Паспорт в проекте — это просто одна из записей `employee_documents`
(`type = passport`), а не поля `employees`. Чтобы номер паспорта был
единым источником для *любого* генерируемого документа (а не только при
генерации самого паспорта), `document_generate.php` подставляет
`${passport_number}` / `${passport_series}` / `${passport_issued_by}` /
`${passport_issue_date}` из паспортной записи сотрудника **независимо** от
того, какой документ генерируется — например, при генерации визы номер
паспорта всё равно берётся из паспорта, если только не переопределён через
`field_overrides` конкретно у визы.

Если у сотрудника несколько записей типа `passport` (старый и новый),
канонической считается запись с максимальной `issue_date`. Жёсткое
ограничение «один активный паспорт на сотрудника» в БД не вводится (риск
при некорректном вводе данных остаётся), но `document_generate.php`
обязан выбирать именно так, а не первую найденную запись.

## Библиотека

**PHPWord** (`phpoffice/phpword`) — заполняет .docx-шаблон по плейсхолдерам
вида `${full_name}` через `TemplateProcessor`, не требует LibreOffice/MS
Office на сервере. Больше никаких пакетов не нужно — без PDF-экспорта
`dompdf` не требуется, зависимость всего одна.

## Конвенция плейсхолдеров шаблона

| Плейсхолдер | Источник по умолчанию | Переопределяемо через `field_overrides`? |
|---|---|---|
| `${last_name}` | `employees.last_name` | да |
| `${first_name}` | `employees.first_name` | да |
| `${middle_name}` | `employees.middle_name` | да |
| `${full_name}` | `employees.full_name` (собран из частей выше) | нет — правится через части |
| `${citizenship}` | `employees.citizenship` | да |
| `${birth_date}` | `employees.birth_date` (формат `дд.мм.гггг`) | да |
| `${position}` | `employees.position` | да |
| `${department}` | `employees.department` | да |
| `${passport_number}` | Номер из **канонической** паспортной записи сотрудника (`employee_documents` c `type = passport`, максимальная `issue_date`) | да |
| `${passport_series}` | Серия из той же канонической паспортной записи | да |
| `${passport_issued_by}` | `issued_by` из той же записи | да |
| `${passport_issue_date}` | `issue_date` из той же записи (формат `дд.мм.гггг`) | да |
| `${document_type}` | Человекочитаемое название типа **генерируемого документа** (`DOCUMENT_TYPE_LABELS`) | нет (определяется типом записи) |
| `${document_number}` | `employee_documents.number` генерируемого документа | нет (это и есть поле документа, не общее) |
| `${document_series}` | `employee_documents.series` генерируемого документа | нет |
| `${issue_date}` | `employee_documents.issue_date` генерируемого документа (формат `дд.мм.гггг`) | нет |
| `${expire_date}` | `employee_documents.expire_date` генерируемого документа (формат `дд.мм.гггг`) | нет |
| `${issued_by}` | `employee_documents.issued_by` генерируемого документа | нет |
| `${generated_date}` | Текущая дата на момент генерации | нет |

`${document_*}` всегда про сам документ, по которому вызвана генерация, —
у него нет «единого источника» (это и есть первичные данные), поэтому
`field_overrides` их не касается. `${last_name}` / `${first_name}` /
`${middle_name}` / `${citizenship}` / `${birth_date}` / `${position}` /
`${department}` / `${passport_*}` — общие данные сотрудника: по умолчанию
из единого источника, но каждое конкретное значение можно переопределить
для этого документа через `field_overrides` (см. раздел выше).

Шаблоны — статические файлы, не пользовательские данные, поэтому хранятся
в `templates/` и коммитятся в git (в отличие от сканов).

## Генерация документа (без сохранения на сервере)

Результат заполнения шаблона отдаётся сразу как скачивание (HTTP-ответ с
`Content-Disposition: attachment`), не сохраняется на диске — меньше
конфиденциальных данных лежит на сервере дольше, чем нужно, и не нужна
уборка временных файлов.

Точка входа: `document_generate.php?document_id=<id>` (за
`requireLogin()`), отдаёт `.docx`.

## Сканы документов

- Расширение таблицы `employee_documents`: `scan_stored_name` (сгенерированное
  имя файла на диске), `scan_original_name` (для отображения),
  `scan_mime_type`, `scan_size`.
- Один скан на запись документа (не несколько файлов/страниц) — если
  понадобится больше одной страницы, сотрудник загружает многостраничный
  PDF.
- Файлы — вне `.docx`-шаблонов, это персональные данные сотрудников, поэтому:
  - хранить с непредсказуемым именем (не оригинальным), например
    `uploads/documents/<random>.<ext>`;
  - каталог `uploads/` — не в git ([.gitignore](../../../.gitignore));
  - **отдавать файл только через авторизованный PHP-скрипт**
    (`document_scan.php?document_id=<id>`, проверяет `requireLogin()`), не
    напрямую статикой — иначе скан можно скачать по прямой ссылке без
    логина, зная/подобрав путь;
  - валидация при загрузке: реальный MIME-тип (`finfo`, не только
    расширение из имени файла), белый список расширений
    (`jpg`/`jpeg`/`png`/`pdf`), лимит 10 МБ;
  - `uploads/` должен быть недоступен для выполнения PHP (на случай если
    злоумышленник как-то загрузит `.php` под чужим MIME) — добавить
    `uploads/.htaccess` с запретом выполнения скриптов, если хостинг на
    Apache (у `ihc.ru`, вероятно, да).

## Затрагиваемые/новые файлы

- `composer.json` — зависимость (`phpoffice/phpword`). `vendor/` не
  коммитится, но обязателен в `deploy/` (см. tasks.md).
- `templates/` — .docx-шаблоны (пока пусто, ждём реальный файл).
- `db/migrations/003_employee_name_parts.sql` — `employees.last_name` /
  `first_name` / `middle_name`; бэкофилл существующих строк из `full_name`
  (эвристически, для старых записей — потребует ручной проверки после
  миграции, см. tasks.md).
- `db/migrations/004_document_scans_and_overrides.sql` — сканы
  (`scan_stored_name`/`scan_original_name`/`scan_mime_type`/`scan_size`) и
  `field_overrides` (`JSON NULL`) в `employee_documents`.
- `employee_form.php` — поля Фамилия/Имя/Отчество вместо одного ФИО;
  `full_name` пересобирается при сохранении.
- `document_generate.php` — заполнение шаблона (единый источник +
  `field_overrides`) и отдача .docx.
- `document_form.php` — редактируемые поля общих данных
  (предзаполненные, с сохранением расхождений в `field_overrides`), кнопка
  «Скачать .docx», форма загрузки/замены скана.
- `document_scan_upload.php` — загрузка скана.
- `document_scan.php` — авторизованная отдача файла скана.
- `uploads/documents/` — рантайм-хранилище сканов (не в git) +
  `uploads/.htaccess`.

## Вне рамок этой фичи

- Экспорт в PDF — сознательно отложен, `.docx` пока достаточно. Если
  понадобится позже: PHPWord умеет и PDF через `dompdf` как рендерер, но
  это приближённая конвертация (через HTML), не honest DOCX→PDF один-в-один
  — стоит отдельно оценить, когда появится реальный шаблон.
- Несколько сканов/страниц на один документ.
- Переход на LibreOffice-конвертацию (требует шелл — недоступен на этом
  хостинге).
- Экспорт сводных отчётов в Excel — это Этап 4.
- UI управления самими шаблонами (загрузка нового шаблона через админку) —
  на первую версию шаблон кладётся в `templates/` вручную, через FTP.
