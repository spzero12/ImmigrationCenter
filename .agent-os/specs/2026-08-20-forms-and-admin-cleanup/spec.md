# Спецификация: Порядок в формах, пользователи, группировка, фото

Пять независимых изменений, запрошенных одним пакетом. Не привязана к
конкретному этапу [roadmap](../../product/roadmap.md).

## 1. Убрать блок «Общие данные сотрудника» с формы документа

По ответу на вопрос: убрать сам блок с `document_form.php` (не только
паспорт из списка типов). Значит:

- Из `document_form.php` пропадают все поля `common_*` (ФИО, гражданство,
  дата рождения, организация, должность, подразделение, паспортные
  данные) и текст-пояснение про переопределение.
- Форма документа больше не пишет `field_overrides` — INSERT/UPDATE
  перестают включать эту колонку. Значения для генерации документа
  (`document_generate.php`) по-прежнему берутся из единого источника
  (карточка сотрудника + связанный паспорт), просто их больше нельзя
  подправить для конкретного документа через UI.
- **Не трогаем** сам механизм в `includes/documents.php`
  (`documentCommonFieldDefaults`, `documentEffectiveCommonFields`,
  `documentBuildOverrides`, колонка `field_overrides` в БД) — он остаётся
  рабочим для документов, у которых `field_overrides` уже был записан
  раньше (`document_generate.php` их по-прежнему учитывает). Это чисто
  упрощение формы, не отказ от данных задним числом.

## 2. Раздел «Пользователи» (CRUD для admin)

Управление системными пользователями (`users`: `admin`/`hr`/`lawyer`/
`manager`) — раньше единственный способ добавить пользователя был
`db/seed.php`. Теперь — полноценный CRUD в UI, доступный только `admin`
(как `audit_log.php`).

- `users.php` — список: логин, ФИО, роль, дата создания. Кнопка
  «Добавить пользователя»; для каждой строки — «Изменить»/«Удалить».
  **Нельзя удалить самого себя** (ни на UI, ни на сервере) — иначе
  admin может случайно остаться без доступа.
- `user_form.php` — создание/редактирование: логин (уникален), ФИО,
  роль (select), пароль (обязателен при создании; при редактировании —
  необязателен, пустое поле = «не менять»).
- `api/users.php` — только `DELETE` (по аналогии с
  `api/employees.php`/`api/documents.php`); создание/редактирование —
  напрямую в `user_form.php`, как у сотрудников и документов.
- Логируется в `audit_log` (`create`/`update`/`delete`, `entity_type =
  'user'`, `entity_label` = логин) — кто именно управляет доступом к
  системе не менее важно, чем кто менял данные сотрудников. Требует
  расширить ENUM `audit_log.entity_type`.
- Пункт навигации «Пользователи» — только для `admin`, рядом с «Аудит».

## 3. Группировка документов по сотруднику

`documents.php` — подзаголовки-разделители в таблице (по ответу на
вопрос), не аккордеон. Порядок сортировки в `api/documents.php` меняется
на `ORDER BY e.full_name, d.expire_date IS NULL, d.expire_date ASC` (было
по сроку истечения в первую очередь) — группировка требует, чтобы
одинаковые сотрудники шли подряд. Внутри группы сотрудника — по-старому
по сроку.

Группировка и построение подзаголовков — на клиенте в `js/documents.js`
(данные уже приходят отсортированными с сервера, скрипт вставляет
`<tr>`-разделитель с ФИО при смене сотрудника). Существующий фильтр по
статусу и поиск по сотруднику не меняются, просто применяются до
группировки.

## 4. Группировка сотрудников по организации

Аналогично — `employees.php`/`js/employees.js`: сортировка в
`api/employees.php` меняется на `ORDER BY organization, full_name`
(было просто `full_name`). Сотрудники без организации — отдельная
группа «Без организации» (в конце или в начале — по алфавиту `''`
сортируется первой, значит группа окажется в начале списка).

## 5. Фото в профиле сотрудника

По ответу на вопрос — те же ограничения, что у сканов документов: JPG/
PNG, до 10 МБ. Отдельно от сканов документов (это фото личности, а не
скан документа), но по той же схеме безопасности:

- `employees.photo_stored_name` / `photo_original_name` /
  `photo_mime_type` / `photo_size` — новые колонки.
- `uploads/employees/` — рантайм-хранилище, не в git (та же логика, что
  `uploads/documents/`; `uploads/.htaccess` уже запрещает прямой
  HTTP-доступ ко всему `uploads/`, включая эту новую подпапку — новый
  `.htaccess` не нужен).
- `employee_photo_upload.php` — приём файла (по образцу
  `document_scan_upload.php`: реальный MIME через `finfo`, whitelist
  jpg/png, лимit 10 МБ, случайное имя на диске, старый файл удаляется
  при замене).
- `employee_photo.php` — отдача файла авторизованному пользователю (по
  образцу `document_scan.php`).
- `employee_form.php` — блок загрузки/замены фото (только при
  редактировании существующего сотрудника — как и скан документа,
  фото нельзя прикрепить, пока карточка не сохранена и нет `id`); показ
  текущего фото как небольшого аватара (Tabler `.avatar`) в шапке формы.
- `employees.php` — маленький аватар в первой колонке таблицы рядом с
  ФИО (или плейсхолдер-инициалы, если фото нет — Tabler это умеет через
  `avatar` с текстом внутри).

## Затрагиваемые файлы

- `db/migrations/007_audit_entity_user.sql` — расширить
  `audit_log.entity_type` ENUM значением `'user'`.
- `db/migrations/008_employee_photo.sql` — колонки фото в `employees`.
- `document_form.php` — убрать блок общих данных и запись
  `field_overrides`.
- `users.php`, `user_form.php`, `api/users.php` — новые.
- `documents.php`, `js/documents.js`, `api/documents.php` — группировка.
- `employees.php`, `js/employees.js`, `api/employees.php` — группировка.
- `employee_form.php`, `employee_photo_upload.php`, `employee_photo.php`,
  `uploads/employees/` — фото.
- `includes/header.php` — пункт «Пользователи» в навигации (только admin).
- `.gitignore` — `/uploads/employees/*` (кроме `.gitkeep`), по аналогии с
  `/uploads/documents/*`.

## Вне рамок

- Самостоятельная регистрация пользователей (только admin создаёт).
- Смена собственного пароля пользователем (только admin меняет чужие —
  если понадобится «сменить свой пароль», это отдельная небольшая фича).
- Обрезка/редактирование фото на лету (кроп, ресайз) — файл хранится
  как есть, только валидация формата/размера.
- Групповые операции (массовое удаление, экспорт группы) — группировка
  только визуальная.
