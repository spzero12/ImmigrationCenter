# Спецификация: Паспорт как единая карточка + поле «Организация»

Не привязана к конкретному этапу [roadmap](../../product/roadmap.md) —
меняет модель данных, заложенную в Этапе 2
([migration-documents](../2026-08-20-migration-documents/spec.md)) и
Этапе 3 ([document-generation](../2026-08-20-document-generation/spec.md)).

## Решение (по ответам на вопросы)

Другие документы (виза, патент, разрешение на работу, регистрация)
ссылаются не «на сотрудника вообще», а на **конкретную запись паспорта**.
`employees` остаётся как есть — ФИО, гражданство, дата рождения и
организационные поля по-прежнему там; паспорт не поглощает эти поля.

Это заменяет текущую логику «канонического паспорта» (самый свежий по
`issue_date`, вычисляется на лету при каждом обращении —
`getCanonicalPassport()` в [includes/documents.php](../../../includes/documents.php))
на явную, зафиксированную на момент создания документа связь. Разница
важна при смене паспорта: сейчас старая виза при выдаче нового паспорта
молча «переезжает» на новый паспорт при следующей генерации документа
(потому что канонический паспорт пересчитывается заново каждый раз); в
новой модели она остаётся привязанной к тому паспорту, который
действовал на момент её оформления — так это работает в реальности с
миграционными документами.

## Модель данных

### `employee_documents.passport_document_id`

Новая колонка `INT UNSIGNED NULL`, ссылается на `employee_documents.id`.

- `ON DELETE SET NULL` — при удалении паспорта связанные документы не
  удаляются каскадно (это были бы визы/патенты, которые физически
  продолжают существовать), просто теряют ссылку.
- Паспорт не может ссылаться сам на себя. Изначально это должен был
  гарантировать `CHECK (type != 'passport' OR passport_document_id IS NULL)`,
  но MariaDB 12.3.2 отказывается добавлять self-referencing `FOREIGN KEY`
  на колонку, участвующую в `CHECK` ("Function or expression ... cannot be
  used in the CHECK clause" — воспроизводится стабильно). В миграции этот
  `CHECK` не используется; правило гарантируется в PHP —
  `document_form.php` всегда передаёт `NULL` для `type = 'passport'`.
- Для типа `passport` поле всегда `NULL`; для остальных типов — обычно
  заполнено, но допускается `NULL` (см. ниже про случай «паспорта ещё
  нет»).

### Бэкофилл существующих данных

Для уже существующих документов (виза/патент/разрешение/регистрация без
`passport_document_id`) — привязать к паспорту сотрудника с максимальной
`issue_date` (то, что раньше вычисляла `getCanonicalPassport()` на лету).
Ограничение: если у сотрудника несколько паспортов с одинаковой/пустой
`issue_date`, бэкофилл выберет один произвольно — это разовая миграция
показания, а не точное восстановление истории (которой в данных просто
нет).

### `employees.organization`

Новое поле `VARCHAR(255) NULL`. По ответам на вопрос: **организация —
это юрлицо-работодатель**, отдельная сущность от `department`
(«Подразделение» — отдел/подразделение внутри этой организации). Простое
текстовое поле в этой версии, без отдельного справочника юрлиц (это уже
следующий шаг, если понадобится — см. «Вне рамок»).

`organization` — часть тех же «общих данных» (`DOCUMENT_COMMON_FIELDS` в
[includes/documents.php](../../../includes/documents.php)), что и
`position`/`department`: предзаполняется на форме документа из карточки
сотрудника, может быть переопределено для конкретного документа через
уже существующий механизм `field_overrides` (менять сам механизм
переопределения не нужно — он уже общий для любого поля из списка).

## Что меняется в коде

### `includes/documents.php`

- `DOCUMENT_COMMON_FIELDS` — добавить `'organization'`.
- `documentCommonFieldDefaults()` — добавить `'organization' => $employee['organization'] ?? ''`.
- `documentTemplatePlaceholders()` — добавить `${organization}` в список
  плейсхолдеров (обновить таблицу конвенции в spec фичи
  document-generation отдельной правкой, когда дойдёт до реализации).
- `getCanonicalPassport()` — не удаляется, но меняет роль: раньше она
  использовалась и для формы, и для генерации; теперь используется
  **только** как подсказка по умолчанию при создании нового документа
  (когда `passport_document_id` ещё не выбран). После сохранения
  документа источником паспортных полей становится конкретная связанная
  запись, а не пересчёт «канонического».
- Новая функция `getLinkedPassport(PDO $db, ?int $passportDocumentId): ?array` —
  просто `SELECT * FROM employee_documents WHERE id = ?`, используется
  везде, где раньше вызывался `getCanonicalPassport()` для уже
  существующего документа (генерация, отображение формы в режиме
  редактирования).
- Особый случай: если генерируется/редактируется сам документ типа
  `passport`, паспортные плейсхолдеры (`${passport_number}` и т.д.)
  берутся из **его собственных** полей (`number`/`series`/`issued_by`/
  `issue_date`), а не через `passport_document_id` (которого у него нет и
  быть не может).

### `document_form.php`

- Для типов, отличных от `passport`, — выпадающий список «Паспорт» с
  паспортами сотрудника (подпись вида `№{number} от {issue_date}`),
  обязательное поле. По умолчанию выбран паспорт, предложенный
  `getCanonicalPassport()` (самый свежий), при редактировании — тот, что
  уже сохранён в `passport_document_id`.
- Если у сотрудника ещё нет ни одной записи паспорта — форма для
  остальных типов документов недоступна с понятным сообщением
  («Сначала добавьте паспорт сотруднику»); создать можно только сам
  паспорт. Это сознательное ограничение — оно и есть смысл фичи
  («паспорт — обязательная точка входа»).
- Смена паспорта в выпадающем списке при сохранении — это и есть
  единственный способ перепривязать документ к другому паспорту, никакого
  отдельного UI для этого не нужно.
- Новое поле «Организация» в блоке «Общие данные сотрудника для этого
  документа» — по аналогии с «Должность»/«Подразделение».

### `employee_form.php`

- Новое поле «Организация» в форме сотрудника (рядом с «Подразделение»).
- В блоке «Документы сотрудника» — по возможности показать, к какому
  паспорту привязан каждый непаспортный документ (например, номером
  паспорта в скобках) — уточнить при реализации, не критично для первой
  версии.

### `document_generate.php`

- Резолвинг паспорта для плейсхолдеров — через `passport_document_id`
  документа (`getLinkedPassport()`), а не через пересчёт канонического.

### Миграция

`db/migrations/006_passport_link_and_organization.sql`:
- `employees.organization`.
- `employee_documents.passport_document_id` + `CHECK` + `FOREIGN KEY`.
- Бэкофилл, описанный выше.

## Обратная совместимость

- Уже сохранённые `field_overrides` на существующих документах не
  трогаются и продолжают работать как прежде — эта фича меняет только
  то, **откуда** берётся значение по умолчанию для паспортных полей, не
  сам механизм переопределения.
- `documentStatus()`, аудит, отчётность (`reports.php`,
  `report_export.php`) не затрагиваются этой фичей — они работают с
  документами и статусами, а не с паспортной связью.

## Вне рамок этой фичи

- Отдельный справочник юридических лиц для поля «Организация» (пока
  просто текст).
- UI для просмотра истории паспортов сотрудника (какие документы к
  какому паспорту привязаны, когда паспорт сменился) — можно добавить
  отдельной фичей, если понадобится.
- Автоматическое уведомление/чек-лист «нужно перепривязать документы» при
  выдаче нового паспорта — новые документы просто создаются уже на новом
  паспорте, старые остаются как есть, никакой автоматики.
